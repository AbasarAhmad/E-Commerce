@Transactional
@Transactional is a Spring annotation used to manage database transactions. It makes multiple database operations work as one unit.

If all operations are successful → Commit (save changes).
If an error occurs → Rollback (undo changes).
Transaction flow:
Begin → Perform Operations → Commit/Rollback → End

ACID Properties
ACID defines the 4 important properties of a database transaction:

Atomicity – All operations succeed, or none of them happen.
Consistency – Database remains in a valid and correct state.
Isolation – One transaction should not interfere with another transaction.
Durability – Once data is committed, it remains saved even after a failure.
Example:
In a money transfer, money is deducted from Account A and added to Account B. If adding money to B fails, the deduction from A is also rolled back.





Persistence Context
A Persistence Context is a temporary working area where JPA/Hibernate manages and tracks entities.
When an entity is loaded inside a transaction:

Product product = repository.findById(id).get();

Hibernate puts the Product into the Persistence Context and starts tracking it.

If we change it:
product.setPrice(1000);

we don't need to call save() because Hibernate uses Dirty Checking to detect the change and automatically sends an UPDATE to the database when the transaction commits.

Easy Flow
Database
   ↓
Persistence Context
   ↓
Managed Entity
   ↓
Change entity
   ↓
Dirty Checking
   ↓
UPDATE Database

In simple words:

Persistence Context is the place where Hibernate keeps and tracks managed entities so it can automatically detect and save their changes.





Interviewer: Why can a JPA entity be updated without calling repository.save()?
Ans : If an entity is loaded inside an active transaction, it becomes managed by the JPA Persistence Context. Hibernate tracks changes to managed entities using dirty checking. When the Persistence Context is flushed, usually around transaction commit, Hibernate generates the required SQL UPDATE automatically. Therefore, explicitly calling save() isn't necessary just to persist changes to that managed entity.





flush():
Flush kya hai?
flush() Hibernate ko bolta hai: "Persistence Context ke pending changes ko abhi DB ke saath synchronize karo."

Kyo zarurat padti hai?
Normally Hibernate transaction ke end mein automatically flush karta hai.
flush() tab use karte hain jab humein SQL ko immediately execute karwana ho ya DB constraint/error ko usi point par check karna ho.

Dirty Checking se kya relation hai?
Dirty checking identify karta hai ki managed entity mein kya change hua.

Entity change
    ↓
Dirty Checking → change detect
    ↓
flush() → UPDATE SQL execute



flush() vs commit()

flush  = SQL DB ko bhejo/execute karo
commit = transaction ko successfully finalize karo

flush() ke baad bhi agar exception aati hai, transaction rollback ho sakta hai.

One-line interview answer
Flush means Hibernate ke pending changes ko DB ke saath synchronize karna; dirty checking changes detect karta hai, flush SQL execute karwata hai, aur commit transaction ko final karta hai.




Transient → New Java object, not tracked by Hibernate.
Managed → Entity is attached to Persistence Context; Hibernate tracks changes using Dirty Checking.
Detached → Entity was managed but is no longer tracked; changes are not automatically saved.
Removed → Entity is marked for deletion; Hibernate executes DELETE during flush/commit.	




| Concept             | What you've practically verified                   |
| ------------------- | -------------------------------------------------- |
| Persistence Context | Hibernate tracks managed entities                  |
| Managed Entity      | Changes are automatically detected                 |
| Dirty Checking      | Changed fields generate `UPDATE`                   |
| `save()`            | Not required for an already-managed entity         |
| `flush()`           | Synchronizes changes with DB                       |
| `commit()`          | Completes the transaction                          |
| Rollback            | Undoes flushed changes when transaction rolls back |
| Detached            | Changes are no longer automatically tracked        |

Flyway — Quick Notes
1. What is Flyway?
Flyway is a database migration/version-control tool.
It manages changes to the database schema in a controlled and ordered way.

Think:
Git → version control for code
Flyway → version control for database changes


2. Why do we use Flyway?

Without Flyway, developers may manually run SQL:

CREATE TABLE products (...);
ALTER TABLE products ADD COLUMN brand ...;

This becomes difficult to track and reproduce.

With Flyway, we keep SQL files in the project:

db/migration/
├── V1__create_products_table.sql
├── V2__create_product_audits_table.sql
└── V3__add_brand_to_products.sql

Now database changes are:

versioned
ordered
tracked
repeatable across environments


3. How does Flyway work?

When the application starts:

Spring Boot
    ↓
Flyway connects to MySQL
    ↓
Checks flyway_schema_history
    ↓
Finds pending migrations
    ↓
Runs V1 → V2 → V3...
    ↓
Records them in flyway_schema_history

Example:

V1 ✓
V2 ✓
V3 pending

Flyway runs only V3.


4. Why don't we let Hibernate create the DB?

We use:

spring:
  jpa:
    hibernate:
      ddl-auto: validate

validate means:

Hibernate does NOT create or modify tables. It only checks whether the database matches the entities.

So responsibilities are:

Flyway
  ↓
Creates/changes database tables

Hibernate
  ↓
Maps Java entities ↔ database
  ↓
Validates database structure

This gives us clear separation of responsibility.



5. After Flyway, why does Hibernate give an error if a table is deleted?

Suppose Flyway created:

products
product_audits

and flyway_schema_history says:

V1 ✓
V2 ✓

Then someone manually deletes:

DROP TABLE product_audits;

Flyway sees:

V2 ✓

and thinks:

"V2 was already successfully executed, so I don't need to run V2 again."

Therefore Flyway doesn't recreate the table.

Then Hibernate starts validation:

ProductAudit entity
       ↓
@Table(name = "product_audits")
       ↓
Does product_audits exist?
       ↓
NO ❌
       ↓
Schema validation error

That's why you got:

Schema validation: missing table [product_audits]
Important rule

Don't manually delete or modify tables that Flyway manages.

If the schema needs to change, create a new migration:

V3__change_product_audits.sql

rather than manually changing the database.

In one line:

Flyway manages database changes; Hibernate validates that the database matches your Java entities.
